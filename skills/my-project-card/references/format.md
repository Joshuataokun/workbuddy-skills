# 分册拆分口径与条目标记规范

## 一、主卡七段

| # | 段名 | 放什么 | 不放什么 |
|---|---|---|---|
| 1 | 项目目标 | 一句话交付物 + 验收对象 | "提升效率"这类空话 |
| 2 | 口径与约束 | 跨工作面都成立的硬规则：发布方式、版本号规则、合规红线 | 单条线的接口细节 |
| 3 | 已排除方案 | 被否掉的方案 **+ 否决原因** | 只是"没做"的 |
| 4 | 已完成 | 已发生的事实，带日期 | 计划中的事 |
| 5 | 当前进度 | 现在在哪、下一步做什么 | 长篇过程 |
| 6 | 待确认 | 用户没拍板的问题 | 自己推测的结论 |
| 7 | 关键位置 | 工作区根 + 分册指针 | 细节清单（进分册） |

## 二、分册六段

| # | 段名 | 放什么 |
|---|---|---|
| 1 | 职责与范围 | 这条线负责什么，边界在哪 |
| 2 | 口径与约束 | 只对这条线成立的规则、命令、预算 |
| 3 | 已完成 | 已发生的事实 |
| 4 | 待办 | 明确的下一步 |
| 5 | 踩过的坑 | 现象 + 原因 + 解法，别人别再踩 |
| 6 | 关键位置 | 文件路径、入口、脚本清单 |

**第 5 段是 2.0 新增的**。它装的是"试过不行"的具体现象，和主卡「已排除方案」的区别是：主卡记的是方案层面的否决，分册记的是操作层面的坑（某条命令的坑、某个格式的坑）。

**拆分口诀**：换一条线就说不通 → 进分册；放哪儿都成立 → 留主卡。
**分册过一屏就该再拆。**

## 三、条目标记

```
- 【确认·YYYY-MM-DD·"用户原话"】#a1b2 条目正文
- 【待确认】#c3d4 条目正文
- 【已失效·YYYY-MM-DD·被 #e5f6 替代】#a1b2 条目正文
```

`#id` 四位十六进制，命令自动生成。作用有两个：`revise --id` 精确改一条；失效条目能指回被谁替代。

| 写法 | 判定 | 原因 |
|---|---|---|
| `- 【确认·2026-10-25·"内网部署"】#a1b2 部署在内网` | 通过 | 有日期有出处 |
| `- 部署在内网` | 拒绝 F03 | 无标记，无法追溯 |
| `- 【确认·2026-10-25】#a1b2 端口应该是 8080` | 拒绝 F04 | 推测词 + 标确认 |
| `- 【待确认】#c3d4 端口可能是 8080` | 通过 | 诚实标注 |
| `- 【确认·2026-10-25】#e5f6 数据库密码: Abcd1234` | 拒绝 F05 | 明文凭据 |
| `- 【确认·2030-01-01】#a0b1 明年上线` | 拒绝 F10 | 未来日期 |
| 与同段某条一字不差 | 拒绝 F06 | 重复记录 |

## 四、拒绝码

| 码 | 触发 | 处理 |
|---|---|---|
| F03 | 缺日期或标记 | 拒绝，文件不动 |
| F04 | 确认项含推测词 | 拒绝，改成 `--pending` |
| F05 | 明文凭据 | 拒绝，改记"凭据在哪" |
| F06 | 与已有条目几乎重复 | 拒绝；要保留加 `--force`，要替换用 `revise` |
| F09 | 覆盖已存在的卡／分册 | 拒绝，除非 `--force` |
| F10 | 未来日期 | 拒绝 |
| F11 | 失效条目引用了不存在的 id | `check` 报错，补引用或改回确认 |
| F12 | 分册缺段 | `check` 报错，补齐六段 |

推断词表：应该、可能是、大概、估计、也许是、我猜、猜测、或许是、看上去像、八成、感觉是、大概率。

## 五、更新时机

| 时机 | 写到哪 |
|---|---|
| 一件事做完 | 主卡 `已完成` 或对应分册 `已完成` |
| 定了新规则／推翻旧规则 | 主卡 `口径`；旧条目用 `revise` 作废，不要手工删 |
| 方案被否 | 主卡 `已排除方案` + 原因 |
| 踩了一个坑 | 对应分册 `踩过的坑` + 现象和解法 |
| 冒出新问题 | `--pending` 进 `待确认` / 分册 `待办` |
| 开工／收工 | `resume` / `release`，让别的会话看到状态 |

不必更新：纯技术问答、查资料、没产生决定的闲聊。

**强制收尾（v2.1.0）**：`resume` 往事件流写一条 `open` 留痕（不改卡片内容）。用户级 Stop 守卫不依赖技能触发，只要当前工作区有卡，每次答完检查「本轮改了文件 + 本轮没写卡」，成立就拦一次并把补卡命令塞回对话；补完卡第二次自动放行。被提醒后仍没补卡记 `miss`，`audit` 可查。守卫一律 fail-open：无卡、无 transcript、纯只读、脚本出错都放行。

## 六、并发约定

| 场景 | 做法 |
|---|---|
| 两个会话同时写同一张卡 | 文件锁自动排队，后到的等前一个写完，最多等 10 秒 |
| 两个会话改同一本分册 | 先 `claim` 打招呼；`resume` 会显示谁在动这本 |
| 会话异常退出没 `release` | 心跳超过 40 分钟自动视为"可能已结束"，不会一直占着 |
| 备份太多 | `gc --keep 40` 只留最近四十份 |
| 守卫拦了收工 | 补一条 `add` 再收工；纯问答被误判就说明理由，第二次自动放行 |
| 想临时停用守卫 | 在卡片库根目录建 `.stop-guard-off`，删掉即恢复 |
| 查谁漏记 | `audit`：读过没写的会话、守卫拦截次数、提醒后仍未补卡次数 |
