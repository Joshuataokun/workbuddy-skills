# 排查手册（debug-playbook）

「功能不工作」的完整排查路径 + 各类经典坑的模式库。适用于服务端有源码的逆向仿制网单（Go/C++ 等）。

## 一、排查四步法详解

### ① 服务端 grep 命令注册
```bash
grep -rn 's.On("命令前缀' /path/to/server/internal/ --include=*.go
```
找到 handler 函数名 → 读函数体。**没有注册的命令**：查 schema_defaults 类文件（命令→响应结构默认值映射），有 schema 无 handler = 未实现（返空结构）。

### ② 看响应结构
```bash
python3 -c "import json; d=json.load(open('schema_defaults.json')); print(json.dumps(d['命令名'], indent=1))"
```
对照客户端期望的字段（下一步）找出**缺失/命名不一致**的字段。

### ③ 日志对照（最有力证据）
```bash
journalctl -u 服务名 --since '10 minutes ago' | grep '命令名'
```
看：客户端到底发了没有（没发=客户端问题）、服务端回了什么 code（1xxx 错误码常对应「未实现/参数错/状态错」）、返回体多大（390B=空 schema，200KB=真数据）。

### ④ 客户端消费字段
bundle 里 grep 命令名的响应处理（`.then` / `getData()`），确认客户端读哪个字段。**经典错配**：客户端读 `score` 而服务端没发 → undefined → NaN → 渲染空白。字段给了但单位错 → 显示 1970/巨大数字。

## 二、诊断注入法（疑难杂症）

客户端内部计算错乱（时间判断/条件分支）无法从外部观察时：**在 bundle 判断处插入常驻诊断代码**，把中间变量显示到界面上：
```js
// 在目标 return 前插：window.__diag = { 中间变量... }
// 在可见 UI 文本处追加显示：window.__diag && (this.ui.m_xxxLbl.text += " [D" + ... + "]")
```
注意逗号表达式位置只能插表达式（见 h5-patch 铁律 2）。用户截图回来就能定位是哪一环错。**诊断代码定位完成后记得删干净再发正式版**。

## 三、存储链规则（改库必读）

典型链路：`CachedStore(内存L1) → RedisStore(L2) → MySQLStore`。

- **改数据库必须：停服 → 改库 → 清 Redis 对应 key → 重启**。否则内存副本会把旧值写回覆盖你的修改
- Redis key 模式：`xy:role:<id>`（角色）、`xy:opsconfig`（运营配置）等，改前先 `KEYS` 摸清
- 领取类操作走事务（claimRewardTx 类），若 Redis 层缺事务支持会返特定错误码（如 1004）——这属于存储层实现缺失
- **客户端读的角色视图有秒级缓存**（roleViewFull 5s 类），改完立刻看界面可能有延迟，等 5 秒再判定没生效

## 四、封禁/解封机制

- 服务端封命令：**disabledPrefixes 前缀表**（Dispatch 层直接返空 schema，不进 handler）。删行重编译即解封
- **加前缀前先 grep 该前缀命中的全部命令**——`card_` 误封卡片订阅、`rank_` 误封排行榜这种事故都源于凭语义猜前缀
- 前缀太宽误伤是这类服务端最常见的人为故障；封之前列清单确认

## 五、时间机制专项

### 单位约定三步确认法
1. grep 客户端该字段**全部**消费点：`×1e3` 后用 = 当秒；直接 `new Date(x)` = 当毫秒；纯比较（差值>60）= 无所谓但通常秒
2. 看同功能别的字段（同类消息里 timestamp 单位往往一致）
3. 改服务端前用 node 复刻客户端格式化函数跑一遍真实值

### 经典坑模式
| 症状 | 根因模式 |
|---|---|
| 显示 1970 年 | 时间戳 0/undefined；或秒被「倒计时归一化」减成剩余几百秒再按绝对日期渲染 |
| 倒计时 600+ 天 | 周基准字段（mondayTimestamp 类）服务端发毫秒、客户端当秒 ×1e3，放大 1000 倍 |
| 倒计时全乱但别的时间对 | 客户端全局 serverTime 被某处下发的秒级 time 覆盖（找 WS 顶层 time 下发点） |
| 全对但界面锁死 | 时间判断其实过了，真凶是业务数据（如报名表为空被判未报名）——**先看诊断数据再怪时间** |
| 每日一次类按钮在归零时点前点了没反应（如服务端归零改凌晨 6 点后的 0-6 点） | 客户端 isToday/todayTime 硬编码 0 点日切、服务端已改时点：客户端判「新一天」亮按钮、服务端判「同一天」拒绝且被吞。修法=客户端加游戏日锚（见 SKILL 时间机制节），isToday/updateTodayTime/倒计时全走它 |

### 倒计时归一化坑（通用模式）
很多游戏的 `getFormatBySecond(seconds, formatId)` 是复用函数：入参落在 `(1e9, 2.2e9)`（2001-2039 的秒）会被当「未来截止时刻」**减去 now** 得剩余秒。倒计时用法正确；**显示绝对日期必须绕过归一化直接调内层日期格式函数**。MySQL `JSON_EXTRACT` 路径**区分大小写**——键 `createTime` 查 `$.CreateTime` 返 NULL，别误判数据缺失。

## 六、领取/邮件类防重发模式

状态机：`1=未读 → 3=已领取 → 9=已删除`。常见 bug：删除只改状态**不清附件**、批量领取只跳「已领取」不跳「已删除」→ 已删邮件附件反复重发。修法：领取过滤条件 `state==3 || state>=9`。GM 后台发的物品被玩家反复领 = 先查这个。

## 七、逆向仿制服务端的共性认知

- 命令返回空 schema + 硬编码 0 = **未实现**，不是 bug；先分类（未实现/配置错/逻辑错）再动手
- **改响应结构改对地方**：客户端读的是 View 函数（roleViewFull 类）不是 store 结构体；改了 store 不改 view = 白改
- 客户端反作弊判断（战力=0/非法操作提示）可能源于**数据不完整**而非外挂——先补数据再看
- 编译部署节奏：改码 → 编译 → 停服 → 换二进制（留 .bak）→ 起服 → 看 active + 日志无报错

## 八、验证纪律

- **node 复刻证据**：把服务端下发值 + 客户端函数逻辑在 node 里跑一遍，输出新旧调用对比（如「修复前：1970年1月1日 / 修复后：2026年11月5日」）——比「已部署请验证」有说服力得多
- 部署验证链：服务 active → 日志无错 → curl 端到端 → 用户 F5 实测截图
- 一次只改一处，改完即验证——多处同改出问题无法归因

## 九、战斗结算专项（引擎自演 vs 服务端近似）

**架构事实**：Cocos 战斗动画由客户端引擎本地演算（输入=双方 team + randomSeed）；服务端 battleData 里的演出明细字段（memos/gameResults/回合数据类）客户端往往**零消费**（bundle grep 0 命中即证）。服务端用别的语言复刻的战斗模拟器只是近似——两边结论可以打架。

**典型症状**：动画演输了，结算屏却弹胜利+发奖（服务端模拟判胜当场结算推层）。

**修法（战后上报架构）**：
1. 服务端：fight_start* 只出演出数据 + 记 pending 标记（如 tower_battle_floor），**不预结算**；上报 handler 信任客户端结局，但加待打值哨兵（上报楼层/关卡必须仍等于当前待打值，结算后清零）——防重复上报、防陈旧上报、防跳关
2. 客户端：battleEnd 回调把 `battleData.result.isWin` 同步成引擎实际结局（**battleEnd 第二参数就是引擎战果**，`e.battleResult || t` 改成优先取 t 或把 t.isWin 拷过去），并按实际结局上报 success/failure
3. 上报调用包 try/catch（WS 瞬断时同步抛错会炸掉整个结算弹窗）；回放模式（replay 标志）不上报

**判别命令名**：客户端 Service 方法名 → 命令=(模块前缀_方法名).toLowerCase()（如 TowerService.success → tower_success）。CDP 直调一次看网关日志即确认。客户端 Service 没有上报方法但服务端有 handler 时照样补——handler 多是逆向时从协议挖出来的，只是客户端断线没接。

## 十、发奖链三查实战（「显示已获得但没到账」）

三层递进的坑，同一条领取链能连环踩（实测连环踩完三层）：

1. **入口被假数据锁死**（第一层）：回包等级字段用「达成推导」算出配置行 id（万级大数），客户端渲染规则 `行号 < curLevel = 已领取` 恒真 → 全列表永久"已获得"不可点。判别：state 里的真领取游标（如 totalClaimed/bookLastReward）从未被写 + 日志零次 claim 命令调用。
2. **回值格式与客户端换算链不匹配**（第二层）：修成回「领取行数」（57）客户端 `getById(57)` 查无 → 等级显示清零。正解=回「已领到的最后一行配置 id」（getById 命中→indexOf+1 得显示等级）。**先读客户端消费代码定格式，再改服务端回值**。
3. **奖励从未入账**（第三层，最狠）：领取 handler 返回 rewards 只进回包 + NotifyReward 弹窗，handler 所在文件 **0 处 applyReward/资产写入**——客户端弹"获得 XX"金币道具从未加过。判别：拉账对不上（金币增量、道具存量来自其他通道）；背包道具数量与领取记录无关。修法=补资产写入 + 批量领取（循环发全部达成档）+ 存量补发（游标>0 的角色一次性补 1..游标 档，幂等标记防重）。
4. **奖励类型枚举两端错位**（伴生坑）：官方配置表里的 type 码与服务端 applyReward 的 type 语义不同（如同为 type 2，客户端弹金元宝/官方表=金币，服务端 switch=钻石）。修法=该链路局部映射，**不动全局枚举**（其他系统还在用原语义）。

## 十一、周期切换与存量迁移（赛季/每日口径变更）

- 周期 key 换对齐（周→天）本身简单：key 计算去掉周期归零 offset，结算触发比较 key 变化，previous 减一个周期。勋章过期=下个周期界时刻。
- **迁移误伤坑**（必踩预警）：存量迁移写「非新 key 全并入新 key」会把**昨天的新格式 key** 也抢走——昨天的分从此无人结算。正解=迁移条件只匹配**旧格式特征**（旧周期 key 的日期必是周一，可 Parse 后判 Weekday），新格式近邻 key 一律不动。
- 测试锁：上线前必须有「昨天 key 有分 → 结算照发」的用例，迁移误伤会被它直接抓出来。
- **计分口径变更先审计再清**：查各计分通道+抽查落库值，若榜单积分全来自将废弃通道（如全服没人打过竞技场但积分榜有分=全是爬塔分），下轮结算前停服清零，否则发一届不合规奖。清零走改库铁律三步。
- 直调 RPC 改完 state 立即读 MySQL 会撞缓存异步 flush 延迟（约 20s），等一下再验账。

## 十二、MySQL 批量改 JSON 字段（三步中转法）

大 JSON 列（如 roles.data_json 半 MB 级）批量修改**不要在 shell 管道里拼 UPDATE**（引号/反斜杠转义地狱，还可能静默截断）：

```
① SELECT 导出逐行 → tsv（python 逐行 json.loads → 改 → dumps → 反斜杠/单引号转义 → "id|json" 行）
② python 读 tsv 生成 .sql 文件（UPDATE ... SET data_json='...' WHERE id=...; 每行一条）
③ mysql 库 < file.sql 一次导入，再 SELECT 验证
```

注意：持久层 JSON 键名可能与内存结构体不同（如 Role.Daily 持久化成 dailyTask），先 LIMIT 1 dump 看真实键名再写改逻辑。

## 十三、多端登录互踢（微信内置浏览器旧页空白专项）

症状：某页面"进入后空白"但本地静态弹窗照常弹、另一端一切正常。链路：登录轮换单值 token → 旧端（微信内置浏览器挂着的旧页）被唤醒 → 带旧 token 重连被拒 → 无退避重连死循环（12 秒 29 次）→ 期间拉不到任何数据=空白。

- 破案证据在**网关访问日志**：同一时段两个 UA（Chrome 正常 + WindowsWechat/XWEB 死循环）、死循环连接带旧 token 且 isRestore=1。
- 修法=登录换 token 时旧 token 进进程内宽限表（24h TTL），verifytoken 主查不到再查宽限表；踢人命令/同 IP 换号登录仍全吊销（安全边界不变）；服务重启宽限清空，主 token 走持久层不受影响。

## 十四、结算弹窗 await 死锁与自动关闭兜底（没点确认就卡死专项）

**症状**：战斗胜利后结算弹窗，用户没点确定/下一关（或点击没命中按钮热区——整十关常是单按钮模式热区更小）→ 游戏卡死：战斗场景冻在最终回合、跳过/倍速按钮还挂着、QUIT_BATTLE 不执行。

**机制**：battleEnd 里 `await SHOW_BATTLE_RESULT(...)` 是**弹窗 close 才 resolve** 的 Promise——面板不关，await 永久挂起，整个结算流程死锁。拖久（2-4 分钟无操作）还会撞 AFK 省电锁屏强关非白名单面板，解锁后 UI 层错乱更难恢复。**进度本身不丢**：战后上报架构在弹窗**之前**已发 success/failure（层数已落库），F5 刷新重进即回正。

**修法（autoCloseTimer 模式门控兜底）**：结算弹窗基类自带每秒滴答的 `autoCloseTimer`（超时 `this.close()`）+ 倒计时文案 `m_autoCloseTips`，但常写死只对个别玩法生效（如 skyHorsePvp 5 秒）——把条件扩到目标模式并给独立兜底时长：`(skyHorsePvp || tower) && (... (options.get(AutoCloseTime) || (tower ? 15e3 : 5e3)) ...)`。自动关闭=等效点"取消"（WindowCloseState 非 Yes），流程照常走完，不触发自动连打/自动领奖，服务端进度早已落定不受影响。

**改错面板教训（血泪）**：胜利/失败是**各带一份 autoCloseTimer 拷贝**的两个弹窗类，压缩后变量别名不同（胜利 d/c/g/T、失败 c/h/y/d）——**needle 唯一性校验通过 ≠ 改对了地方**：曾拿失败弹窗的锚点（c/h/y/d）去打"胜利面板补丁"，count==1 断言通过、日志自报"已修复"，实际胜利路径从未被修，同一 bug 次日复发。防重演三道闸：
1. 补丁脚本里 assert 锚点位置落在 `目标模块名: [ function` 到下一模块边界之间；
2. 打完后验证**每个**相关弹窗模块的区间（不是全文件）都含目标 needle；
3. 排查报告里"改了哪个类"必须引用模块名原文，不能只写意图。

**验证**：python 抽查新 bundle 两个弹窗模块区间均含 `BattleType.tower + 15e3`；curl 双路（plain+gz）200；用户 F5 后打一场实测不点、等倒计时走完自动关。

## 十五、删号 SOP（全痕迹清查 + 可回滚，脚本化）

删号=改库，走完整铁律，且必须**全痕迹清查后再动手**（逆向服的账号体系横跨多库：游戏库存账号/角色/关联表，运营后台库存玩家/游戏角色/流水/订单，Redis 存角色与 token 键——外键常是 username 或 role_id 字符串，逐表 DESCRIBE 确认列名再查）。

固定流程五条：
1. **痕迹范围清单**：账号表、角色表、role_id 关联表（英雄/装备/邮件/订单/聊天/活动/领取记录）、好友与好友申请（**双向列**，如 role_id+friend_id、id+to_id）、运营库玩家表+游戏角色表+流水+订单、Redis 角色键
2. **脚本化 + 双模式**：默认 dry-run 只列删除清单不动数据，人工确认后 `--yes` 才实删——「先列清单等拍板」在删号上必须是硬约束
3. **实删六步**：mysqldump 按行备份（--where 精确导出，可回滚）→ 停角色相关服务（网关/交换服不连角色库可不停）→ DELETE（先子表后父表）→ FLUSHDB → 重启 → 全表复验零残留 + 服务全绿
4. **保护栏**：主号/管理员账号硬拒删（名单写死在脚本）；账户余额或充值记录非零必须警示（删=作废）
5. **收尾**：对已删账号跑一次定位查询应返回「不存在」；Redis KEYS 确认无残留

配套规矩（用户指令）：**测试账号测试完即删**，不留「留档」探针账号——「留档可回滚」不是保留账号的理由，mysqldump 备份才是。

## 十六、数值加成系统判别（配置在≠生效，显示≠实战）

逆向服里「描述说有加成」的系统常是纯展示。用户问「这套加成发挥作用了吗」时按三查判别：

1. **配置在不在**：数据包该表有没有属性类字段（如 stageAttrReward/attrs）
2. **显示链路在不在**：客户端弹窗/列表读不读它（有→用户看得到数值，容易误以为生效）
3. **实战链路在不在**：两端战斗构建有没有消费——服务端 grep 属性注入钩子链（decorate*Fighter / apply*TeamEffects 系），客户端 bundle grep 字段名统计消费点（全在弹窗渲染=零实战消费）

显示在+实战零消费=「纸面加成」。落地模板：仿既有全队注入钩子直接改 fighter 字段（attack/hp/curHp）——客户端引擎与 Go 模拟器同源消费，一处挂点（battleTeamForRole 类函数）全链路生效（PVE/竞技场双端对称）。两个坑：
- **累计制配置陷阱**：行值已是历史累计（第 N 行=总加成），取已领最后一行直接加；对全部行求和=放大几十倍
- **属性类型对照**：以生产配置数值+用户界面显示交叉验证（如 type1+8200 显示为「攻击加成」→ type1=ATTACK_ABS），别猜枚举


## 十七、商店经济学研究法（充值性价比/渠道对比专项）

症状：用户问「钱怎么花最值」「某渠道和某渠道哪个划算」。本质是把每个渠道折成「每元买到的战力」排序。2026-11-08 实战定型的四步法：

**第一步：战力密度折算标尺**（先建立折算系数，全渠道共用）
- 从战力公式（PowerOf 权重）推出每种材料换多少战力：如主力定向红碎=升一星所需碎片数 ÷ 单英雄战力×星数百分比（例：5-10 星档 40 碎=+10%=850 战力/个）
- 乘区系统（升星/进阶）是高杠杆大头：进阶表逐阶 ×1.1 全属性，3000 石/阶 → 进阶石 11.3 战力/个，往往是战力密度最高的日常材料
- 线性系统（等级/装备）边际递减，折算时用用户当前进度区段的边际值

**第二步：渠道三查（单价 × 池子权重 × 限购周期）**
- 单价：游戏内商店金砖价、直充档金砖/元汇率、卡券折算（周卡/月卡/终生卡的每日奖励÷价格——卡券效率常是直充的几百倍）
- 池子权重：**奖池代码必须全量拉完**（reward 数组逐行加总权重算每项概率）——截断读取只看前 N 行会漏主体误判（实战：金杆池前 17 行像纯神器池，31 行全表拉完发现与普通池主体完全相同，「零红碎」判断翻车）
- 限购周期：ActivityConf.periodType 语义（服务端 activityPeriodStart 实现）：**0/未知=计数永久累计，1=每日重置，2=每周，3=每月，4=每年**——同一个 limit 数字，语义天差地别（9999 份永久 vs 9999 份/天）

**第三步：开包链路闭合**（礼包/福袋不是终点）
- type 5 道具走 item_openpack → PackConf 的 DiamondPackRewardWeight 权重表算期望产出（例：进阶石福袋期望 169 石/袋）
- 金币包类特判（openGoldPack：秒数×10）

**第四步：口径分层输出**（报告三段式）
- 提升方式排序（按杠杆）→ 材料获取途径与性价比（只列用户实际可用的渠道）→ 每日预算分配方案
- **渠道可用性必须实测验证**：配置表存在+商店列表有 ≠ 入口可见（客户端活动入口有排除数组+总开关，用户实测「封禁/不可见」的渠道不要进推荐）

## 十八、入口开关三层取值链（配置在但功能不可见专项）

症状：配置表、命令处理器都在，用户却看不到入口/活动。2026-11-08 每日特惠案例的完整排查链：

1. **客户端入口过滤条件**：搜活动列表构建代码（_activityList.filter / excludeTypeArr 排除数组 / id!==N 硬排除），确认有没有总开关把该类型过滤掉
2. **开关枚举值**：SwitchId 枚举定义（通常在登录包 assets/main/，值是字符串键名如 DailySpecialSwitch）
3. **取值链逐层查**（checkSwitch 实现）：
   - 服务器登录响应 config 字典（服务端 grep 下发处）→ 没有
   - ops_defaults.json 的 manifest 字段（服务端 applyManifestConfig 合并口）→ 没有
   - 平台远程开关服务（HortorSwitch 类，check 查不到时**硬编码 return false**）→ 私服不存在该服务 = 永久 false
4. **修复通道**：ops_defaults.json manifest 加 `"开关键名": 1` + 重启（opsDefaultsCache 启动时缓存）——这是 ops bootstrap 的官方设计用途，不用改客户端发版
5. **连带影响**：开关打开会带回该功能下全部配置档位（如特惠的低价金砖档），开前评估数值影响
