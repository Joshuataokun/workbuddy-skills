# 目标模型适配 — 判据与已知坑

同一段提示词换模型就失效，多数不是提示词写错，而是**目标模型的行为特性**没对上。写之前先定目标（默认 WorkBuddy 指令框），再按下面这张表改写法。

## 1. WorkBuddy 指令框（默认）

- **载体事实**：输入框是纯文本，Markdown 表格、`<br>`、嵌套代码块粘进去会散；换行与编号是唯一可靠的结构。
- **必须遵守**：一条规则一行；用 `1. 2. 3.` 或 `- ` 平铺；不用表格；不用 HTML；标题用「一、二、」或「## 」之外的纯文本行。
- **长度**：一次贴进去能滚两屏以内最好；超过就把背景压成三条事实。
- **常见坑**：把「变量/参数」写成花括号占位却忘了说要替换；依赖系统自带能力（如"用你的知识库"）而当前会话没有该工具——写成条件句「若你有联网能力则……，否则……」。
- **判据**：把这段提示词粘进输入框，结构是否还清楚？表格是否变成一堆竖线？变成就是不合格。

## 2. 通用对话模型（DeepSeek / GPT / Claude / 豆包 / Qwen / GLM）

按行为分两类，先判类再写：

**A. 字面执行型（Claude 4.x 一类）**
- 说多少做多少，缺的背景不会自己补——补过头是另一种错，补不足会给出窄而浅的结果。
- 写法：背景、输入、验收标准**前置**写全，一次给完；加一句「只做要求的改动，不额外发挥」。
- 别加「一步步想」「充分思考」这类元指令：新一代模型自适应调节深度，硬加反而挤占预算。

**B. 推理型（o 系、R1、thinking 模式）**
- 内部自带推理，不要索取思维链、不要给固定思考步数。
- 要的是：结论 + 依据 + 假设 + 验证方式，四样齐；说「不确定就标不确定」。

**通用要点**
- 中文模型对软化词（尽量/适当）比英文模型更敏感地"松弛"，规则要用阈值与清单锁死（见 `zh-pitfalls.md`）。
- 长提示词中段最容易被忽略：把最硬的 3 条规则放在开头和结尾各一次（重复允许，矛盾不允许）。
- 输出格式要写成"模板 + 一个例子"，只在文字里描述格式，漂移概率明显更高。
- 跨模型复用时，把验收标准写成可观察项（数量、字段、单位、允许的词表），这是唯一跨模型稳定的部分。

## 3. 代码 / Agent 指令

- **必须写死的三件事**：出错是停下问还是按默认继续；可读写的边界（只读？禁碰哪些目录/命令？）；验收方式（跑什么测试、贴什么输出）。
- 不许出现"适当处理错误"这类软表述——换成"重试 N 次后仍失败则停止并报告原始报错"。
- 工具调用要有白名单；删除、覆盖、推送这类不可逆动作，一律先确认。
- 判据：一个新同事只看这段指令，能否在不问你的情况下判断"该停还是该继续"。

## 4. 出图 / 多模态

- 正向描述优先；否定句（"不要有文字"）常被理解成"要有文字"，改写成"画面内无任何字符，纯色背景"。
- 结构化标签比长句稳：主体 → 场景 → 光线 → 风格 → 画幅。
- 可控参数（比例、风格强度、负面词）单列，不塞进正文描述。
- 判据：同一段提示词连跑三次，主体与画幅是否稳定。

---

## 用法

守卫模式第 3 步（授权清单）里加一问：目标是谁？用户没说就默认 WorkBuddy 指令框，并写进摘要。若目标与原稿明显不符（例如原稿是给 API 的 JSON 结构，却要贴进对话输入框），属于 C 项级改动，必须先确认再改。
