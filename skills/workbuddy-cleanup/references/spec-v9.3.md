# 1. 启动

## 1.1 锁

```
$WB = 'C:\Users\Administrator\.workbuddy'
锁文件 $WB\cleanup.lock = {"pid":<int>,"startedAt":<毫秒>,"host":"<主机名>"}
```
锁存在、距 now < 90 分钟、pid 仍存活 → 输出「另一清理实例运行中，本次跳过」并结束。
pid 不存在或超 90 分钟 → 僵尸锁，接管。
结束删锁（try/finally）。

## 1.2 策略

读 `$WB\cleanup-policy.json`（唯一策略源）。读不到或损坏 → 用下文内置默认值，报告注明「策略文件缺失，用内置默认」。

可删范围只有四处：`autoDeleteWhitelist`、`quarantine.autoRelease`、`retention.enabled + classes`、`spaceQuarantine.enabled + candidateRule`。`guards.activeHours` 是活动守卫；`quarantine.ttlDays` 是隔离期；`retention.classes[].ttlDays` 是回滚/备份期限；`spaceQuarantine.ttlDays` 是已删空间隔离期；`retention.exclusions` 是永久保留白名单；`report` 控制报告条数。策略里的 `note` / `authorizedBy` / `guardNote` / `firstRun` / `*Note` 是注释，不作为开关读取。

**期限数字一律读策略，不许写死在脚本里**（用户改策略即改行为）。策略 `neverTouch` 是红线清单，`neverTouchNote` 说明两处唯一例外。

## 1.3 计划冻结（防"扫描后被改动的文件被误删"）

先扫描、后执行，两阶段分离：

1. **扫描阶段**：只枚举、只 `Get-Item`，不删任何东西。四类动作各产出一份计划文件：缓存 `plan-<yyyyMMdd-HHmm>.json`、隔离区 `release-<ts>.json`、到期回滚/备份 `retention-<ts>.json`、已删空间候选 `spaces-<ts>.json`。每条形如 `{"path":...,"size":...,"mtime":<tick>,"rule":"logs"}`（第三类另有 `class` / `ageDays`；第四类另有 `dir` / `files` / `lastWrite` / `aliveSessions` / `hasDisplayName` / `reason`）。
2. **执行阶段**：**只按计划文件里的路径删/移，绝不重新枚举目录。** 删前逐条复核：`Test-Path` → 重取 `size` 与 `mtime` → 与计划不一致（被改动过）→ 跳过，计入 `skipped_changed`。

扫描后新增或改动的文件，一律不进入本次动作。

## 1.4 降级

数据库读不出 → 标 `DB_UNREADABLE`，跳过依赖会话数据的统计，**第 2.6 节的会话回滚类与第 2.7 节整节跳过**（都需要活会话判定），缓存清理、隔离区释放、`backups\` 与编辑历史索引两类照常。被锁时等 60 秒重试一次。

# 2.5 自动释放：隔离区到期批次（第二类自动删除）

用户 2026-11-04 原话：**「下次执行清理任务，自动检测超期隔离的文件，自动删，我没有那么多精力想这么多事」**。
所以本步**不接受口令，每次运行开头主动执行**。范围**只有** `cleanup-policy.json` 里 `quarantine.roots` 列出的隔离根，当前是两个：

- `E:\WorkBuddy\.trash-quarantine`
- `C:\Users\Administrator\.cleanup-quarantine`

第 2.7 节移入的已删空间目录也是这里的批次，同样按本节五条判定释放，不另开通道。

## 2.5.1 判定：五条全满足才释放，缺一即跳过

1. 批次目录是**隔离根的直属一级子目录**，名字匹配 `^\d{8}$`（如 `20261104`）。更深层一律不扫。
2. **路径断言**：批次完整路径规范化后必须以某个隔离根 + `\` 开头（大小写不敏感）。断言失败 → 计入 `refused`，不删。
3. 批次内有 `manifest.json`，能解析，且 `items` 是非空数组。**缺失、损坏、`items` 为空 → 一律不释放**，只入「需你确认」。允许 manifest 位于批次一级子目录内（20261104 就是这种结构），但必须能解析且给出非空 `items`。
4. **到期时间取两个时间点中较晚的一个**：批次目录名对应的本地日期 00:00，与 `manifest.createdAt`。`now − 较晚者 ≥ ttlDays × 24h`（`ttlDays` 读策略，缺省 7）。任一算不出 → 不释放。
5. 批次内**没有** `activeHours`（缺省 24h）内被写入的文件。命中 → 本轮延后，报告注明「有近期写入，延后释放」。

## 2.5.2 执行：先冻结，再按清单删

1. **先冻结清单**：待释放批次写成 `$WB\cleanup-runs\release-<ts>.json`，每批记 `batch` / `root` / `files` / `bytes` / `manifestOk` / `ageHours`。
2. **只按清单删，不重新枚举目录**。单批用三步法：逐文件删 → 子目录按路径长度倒序删 → 删根目录。**禁止 `Remove-Item -Recurse`**（会 fail-closed 且删一半）。
3. 顺序固定：先删批次内的内容，**最后**删 `manifest.json` 与批次目录本身。中途 manifest 丢失 → 立即停手，报告该批「释放中断，manifest 已消失」，不再动同批剩余内容。
4. **逐批回读**：删完立刻 `Test-Path` 批次目录，仍存在 → 计入 `failed`，给完整路径，入「需你手动处理」。

## 2.5.3 回读与记账（强制）

- 两个隔离根各记**删前 / 删后**文件数与 MB，写进报告。
- 记 C 盘与 E 盘可用空间的删前 / 删后。
- **若隔离区已清零但可用空间基本没变** → 说明实体进了回收站，报告写「已移出隔离区，实体进回收站，需你手动清空才真正释放」，**不许写"已释放 X MB"**。
- 本步释放量**单独计数**，不得混进缓存释放量或 2.7 的移入量。

## 2.5.4 红线

- 只删隔离根内的批次目录，**绝不**顺着 manifest 里的 `from` 路径去删原位置。
- `README.txt`、`.meta.json`、任何名字不匹配 `^\d{8}$` 的条目一律不动。
- **未到期批次一个字节都不动**，只报还剩几天。
- 释放前不得修改任何 manifest（只读），也不得往隔离区写任何东西。

## 2.6.1 三类范围与计时依据（**期限一律读策略 `retention.classes[].ttlDays`，本节不写死天数**）

| 类目 | 路径 | 计时依据 |

2. **到期**：`age ≥ ttlDays × 24h`；任一时间算不出 → 跳过，入「需你确认」。
3. **活动守卫**：目标内没有 `activeHours`（24h）内被写入的文件；命中 → 整个会话/条目延后一轮，报告注明「有近期写入，延后」。
4. **会话正文存在**：删会话回滚前，必须能在 `projects\` 找到该 sid 的 `*.jsonl`（证明不是误认）；找不到 → 跳过并入「需你确认」。
5. **永久保留白名单**：sid 前 8 位 ∈ `retention.exclusions` → 整个会话跳过。
6. **命名文件灾备**：本步开始前，先把 `workspace-display-names.json` **字节级复制**一份到 `$WB\cleanup-runs\names-snapshot\`（不在 `workspace\sessions` 下），并校验 SHA256 一致；复制或校验失败 → **整个 2.6 中止**。理由：11-04 侧边栏名字全丢时靠 `modify_backup\1.d.*.workspace-display-names.json` 恢复，清了回滚不能再没恢复源。
7. **绝不触碰**：空间目录、会话正文 `*.jsonl`、`projects\`、`workbuddy.db`、`workspace-display-names.json` 原件、活空间任何文件、隔离区、回收站、0 文件会话空目录。

## 2.6.3 执行：先冻结，再按清单删

## 2.7.1 候选判定：四条全满足，缺一即排除（判定只读）

1. 目录是 `E:\WorkBuddy` 的**直属一级目录**，名字不在 `candidateRule.excludeDirNames`（含 `.trash-quarantine`）。

- 有任一活会话 → 排除。实测 `Claw`：不在 `workspaces` 表，但有 1 个活会话 + 显示名，是活空间。

1. **命名文件灾备**：把 `workspace-display-names.json` 字节级复制到 `$WB\cleanup-runs\names-snapshot\`，校验 SHA256 一致；失败 → 整个 2.7 中止，报告「命名文件灾备失败，本轮不移动任何空间」。理由见第 11 节 11-04 事故。
2. **清单冻结**：只按 `spaces-<ts>.json` 里的路径移动，不重新枚举目录；移动前重取体积与最后写入时间，与清单不一致 → 跳过，计入 `skipped_changed`。
3. **同盘移动**：目标必须是 `spaceQuarantine.quarantineRoot`（E 盘），保证是元数据改名而非跨盘复制；**禁止跨盘、禁止"复制后删源"**。整目录含全部文件一起移。
4. **DB 灾备（v9.4 新增，3a 前提）**：删 `workspaces` 表行之前，用 SQLite online backup（含 WAL）把 `workbuddy.db` 字节级备份到 `cleanup-runs/names-snapshot/workbuddy.db.before-spaces`，校验 SHA256；失败 → 不执行任何删行。`workspace-display-names.json` 原件和任何会话记录始终不改。

## 2.7.3 执行与回读

1. 目标路径 `<隔离根>\<yyyyMMdd>\<原目录名>`，写 `manifest.json`（格式同第 6 节，`reason` 写明「v9.4 方案 C：已删除空间隔离（含文件，同步删DB行）」）。
2. 逐个候选 `os.rename`（同盘元数据改名）；移动后 `Test-Path` 源为 False、目标为 True 才算成功，否则计入 `failed` 并**中止后续候选**。
3. **应用重建检查**：移动后回读 `E:\WorkBuddy` 一级目录；若应用按旧路径自动重建了同名空目录，**不二次移动**，只报告「应用已重建空壳，需用户在侧边栏删除」。这是实测行为，重复移动会造成两个空间。
4. **DB 同步删行（v9.4，3a）**：移入成功后，删除 `workspaces` 表对应路径行。范围严格限定两类：①本轮成功移走的源路径；②磁盘源已不存在、且隔离区某批次 manifest 的 `from` 字段能对上的孤儿行（修复历史遗留——目录已隔离但 DB 行还在，导致下拉仍显示时间戳）。**必须与 manifest 交叉验证**，无 manifest 证据的路径一律不删。事务化执行、逐条回读、幂等；删前已完成 DB 备份（2.7.2 第 4 条）。结果记入 `phase_spaces.db_sync`。
5. 报告给「候选数 / 已移入 / 排除原因分布 / 隔离批次号 / 到期日 / 移入体积 / DB 删除行数」；移入量**单独计数**（`lastSpaceQuarantineMB`），不得混进缓存、隔离区释放或 retention 释放量。**移入不等于释放空间**，不许写「释放 X MB」。
6. 真正释放仍由第 2.5 步统一处理，本节不直接删隔离区内容。

## 2.7.4 红线

- **绝不直接删空间目录**，只移入隔离区。
- **绝不**动有活会话、有显示名、24h 内有写入的目录（v9.4 已无体积上限）。
- **绝不**改 `sessions` 表任何一行；`workspaces` 表只在 2.7.3 第 4 条授权范围内、经 manifest 交叉验证后删行，**其余路径一行不许多删**——V6 验收要求减少行数精确等于 `db_sync.deleted`，多一行即判失败。
- **绝不**碰 `.trash-quarantine` 自身、`projects\`、会话正文 `*.jsonl`、回收站、`workspace-display-names.json` 原件。
- 本节产生的批次仍须满足 2.5.1 五条判定才释放，本节不得绕过。

# 11. 工程注意（每条都踩过）

- **2026-11-04 事故**：上一版删掉 5 个空壳空间后，应用重算工作空间把 `workspace-display-names.json` 整份删掉，侧边栏名字全消失。恢复靠 `modify_backup\1.d.*.workspace-display-names.json` 字节级复制。**结论：删/移空间会连带删名字；2.6 与 2.7 开始前必须先留独立快照并校验 SHA256。**
- **应用会按旧路径重建空目录**：移动空间目录后，应用可能立刻重建同名空壳（与"空间改名不能动磁盘目录名"同源）。**不许二次移动**，只报告并提示用户在侧边栏删除，否则变成两个空间。
- **`workspaces` 表只有 `path` / `last_opened_at` 两列，没有 deleted_at**：不能拿表里有行/没行判断"用户是否删过空间"。2.7 的"已删除"只能靠「0 活会话 + 无显示名 + 24h 无写入 + 近空」四条间接推断，宁可漏判不可误判。
- **`时光杂货` 案例**：11-09 20:07 仍有写入，虽然 0 活会话且无显示名，也必须被 24h 活动守卫排除。**"0 活会话"不等于"没在用"**。
- **`Claw` 案例**：不在 `workspaces` 表却有 1 个活会话和显示名 —— 是活空间，注册不同步而已，绝不入选。
- **禁止 `Remove-Item -Recurse` 删目录**：safe-delete 对非空目录 fail-closed，且失败前会先移走部分子文件。必须三步：逐文件 → 子目录按路径长度倒序 → 删根。
- **删文件必须逐文件，禁止管道**：`$items | Remove-Item` 在第一个异常处中断整条管道，只删 1 个且不报错。
- **删除语句只用 `-ErrorAction Stop`**，吞错只允许在 `try/catch` 里。
- **safe-delete 删成功也会抛错**（`[safe-delete][SAFE_DELETE_FAIL_CLOSED] {... "detail":"OK ..."}`），此时文件其实已消失。成功与否一律 `Test-Path` 复核。
- **删完必须看可用空间，不能只看目录消失**：2026-11-09 实测 Python `os.remove` 删 1050 文件 / 774 MB 全进 C 盘回收站，目录清零但可用空间只从 120.09 → 120.08 GB。必须同时量目录、可用空间、回收站三者，任一不吻合就如实报「未真正释放」。
- **移入隔离区也不等于腾空间**：2.7 的 `lastSpaceQuarantineMB` 是"移入量"，真正释放要看 2.5 到期后回读的可用空间，两者不许混写。
- **`$HOME` 是 PowerShell 只读变量**：用 `$WB`。
- **同一命令可能执行两次**（沙箱 + 提权），脚本必须幂等。
- **数据库只读**：不执行任何 INSERT/UPDATE/DELETE，查询一律 `mode=ro`。
- **不拿间接指标归因**：可用空间受他人干扰，不算证据；要证明删了就量目标目录。
- **会话目录数 ≠ 有内容会话数**：2026-11-09 实测 106 个会话目录里 52 个是 0 文件空壳，只报告不删。
